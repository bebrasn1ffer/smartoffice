только схемы и результаты; цифры и детали говорим голосом.

**Тезисы:**

- в серверной должно включаться охлаждение при росте температуры;
- сотрудник видит состояние с рабочего места;
- до реального монтажа показываем работающий прототип.

**Говорим:** «Задача — не картинка, а работающий стенд: датчики, вентилятор, база, мониторинг,

## Слайд 4. Путь данных (40 секунд)

**На слайде:** одна схема-стрелка:

```
TEMP-01/HUM-01 (каждые 5 с)
   ├→ CTRL-01:8080 → /metrics → Prometheus → Grafana → письмо
   └→ DB-01:8081 → SQLite → веб-история
FAN-01: >30 °C → ON иначе OFF → CTRL и DB
```

**Говорим:** «Одни и те же показания идут в двух направлениях: приложение для мониторинга и
база для истории. Приёмники независимы — отказ одного не останавливает второй.»

---

## Слайд 5. Управление вентилятором (40 секунд)

**На слайде:** скриншот потока Node-RED (`evidence/06_поток_Node-RED_Умный_офис.png`) +
подпись правила: «больше 30 °C — ON, иначе OFF, mode = auto».

**Тезисы:**
- inject каждые 5 с → change (формирует показание) → http request;
- switch по температуре → два отдельных change: ON и OFF;
- поля: `fan.state`, `fan.actuator_id = FAN-01`, `fan.zone = server_room`, `fan.mode = auto`;
- проверка границы: 29,9 → OFF, **30,0 → OFF**, 30,5 → ON.

**Говорим:** «Порог строго «больше 30» — на границе ровно 30,0 вентилятор остаётся
выключенным, это проверено отдельным тестом.»

## Слайд 6. Хранение данных (40 секунд)

**На слайде:** слева — схема двух таблиц (`measurements`, `actuator_events`), справа —
скриншот веб-истории (`evidence/05_веб-история_SQLite_DB-01.png`).

**Тезисы:**
- `measurements` — показания (device_id, metric, zone, timestamp, value, unit, labels);
- `actuator_events` — события вентилятора (state ON/OFF, mode);
- веб-страница: последние значения, график, таблица, выгрузка CSV, копия базы;
- сейчас в базе десятки тысяч записей, интервал ровно 5,0 с.

**Говорим:** «Приёмник проверяет структуру таблиц и целостность базы при старте — база не
создаётся «на лету», это осознанное решение.»

**На слайде:** скриншот панели (`evidence/01_панель_Grafana_штатный_режим.png`).

## Слайд 9. Оповещения и реальные письма (50 секунд — ключевой слайд)

**На слайде:** две колонки: слева таблица правил (2–3 строки), справа — список писем из Gmail
(`evidence/08_письма_Gmail_подтверждение.txt`, можно оформленное письмо).

**Тезисы:**
- TEMP-01 и HUM-01: возраст > 20 с **при доступном CTRL**; оценка 10 с, Pending 0 с;
- CTRL-01 отдельно: `up == 0`;
- письма: `[FIRING:1] TEMP-01` 17:42, `[RESOLVED]` 17:46; `[FIRING:1] HUM-01` 17:49,
  `[RESOLVED]` 17:52 — внешняя почта.

**Говорим:** «Важно: пропажа датчика не подменяется падением приложения — правила датчиков
проверяют ещё и `up`. Письма реальные, с временем, ящик внешний.»

## Слайд 10. Испытания и найденные ошибки (60 секунд)

**На слайде:** таблица 4 строки (сценарий → результат) и рядом 3–4 строки «что исправлено».

**Испытания:**
| Сценарий | Результат |
|---|---|
| TEMP остановлен | возраст 9→59 с, up=1, HUM жив, Firing, письмо |
| HUM остановлен | возраст 9→64 с, TEMP жив, Firing, письмо |
| CTRL остановлен | up=0, метрики датчиков исчезли, Firing только CTRL |
| Нагрузка на БД | 10 чтений + 5 записей: без блокировок, summary 0,49 с |

**Что исправлено (кратко):**
- дублирующая вкладка в Node-RED удваивала данные (38 → 16 узлов);
- база «залипала»: приёмник не закрывал соединения → добавили закрытие и busy_timeout;
- медленные запросы → GROUP BY + индексы (было 30+ с, стало 0,5 с).

**Говорим:** «Это не украшение отчёта — каждая ошибка найдена на стенде и проверена повторным
тестом.»
